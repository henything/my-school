# Азбука движения — Acceptance Criteria

**Проект:** Азбука движения  
**Бизнес:** Азбука движения  
**Тип документа:** Acceptance Criteria / Критерии приёмки  
**Версия:** v1.0  
**Дата:** 2026-06-02  
**Язык:** русский  
**Назначение:** проверяемые критерии готовности MVP v1 для разработки, тестирования и приёмки результата.

---

## 1. Назначение документа

Этот документ фиксирует критерии приёмки первой версии **Азбука движения** — внутренней операционной системы для **Азбуки движения**.

Acceptance Criteria нужны, чтобы:

- ставить задачи Codex небольшими проверяемыми блоками;
- проверять результат разработки;
- писать автотесты и ручные тест-кейсы;
- контролировать границы v1;
- не допустить случайного добавления родительского кабинета, онлайн-оплаты, чата и других non-goals;
- убедиться, что система закрывает основную операционную боль: расписание, посещаемость, списания, переносы, долг и допуск.

---

## 2. Главный критерий готовности v1

MVP v1 можно считать готовым к первому внутреннему запуску, если система позволяет пройти полный операционный цикл:

```text
Создать филиал → создать тренера → создать группу → добавить ребёнка → создать расписание → сгенерировать занятия → тренер отмечает посещаемость → система списывает занятие / создаёт перенос / контролирует долг / показывает допуск → админ видит задачи и проблемы.
```

Главная метрика успеха MVP:

```text
95%+ занятий имеют заполненную посещаемость в день проведения.
```

---

## 3. Формат критериев

Критерии сформулированы в стиле:

```text
Given — предусловие
When — действие
Then — ожидаемый результат
```

# 4. Глобальные критерии v1

## AC-GLOBAL-001 — Система является внутренней системой Азбуки движения

**Given:** пользователь входит в систему  
**When:** он работает с интерфейсом  
**Then:** система не предлагает выбрать другую школу, создать SaaS-аккаунт или пройти публичный onboarding.

## AC-GLOBAL-002 — В v1 нет родительского кабинета

**Given:** система запущена  
**When:** пользователь просматривает доступные роли и интерфейсы  
**Then:** в системе нет роли Parent и нет родительского кабинета.

## AC-GLOBAL-003 — В v1 нет онлайн-оплаты

**Given:** ADMIN работает с абонементом  
**When:** он открывает блок оплаты  
**Then:** система позволяет только вручную менять статус оплаты и не содержит интеграции с платёжным провайдером.

## AC-GLOBAL-004 — В v1 нет встроенного чата

**Given:** пользователь открывает карточку ребёнка или родителя  
**When:** он ищет коммуникацию  
**Then:** система показывает телефон/VK, но не содержит встроенный чат.

## AC-GLOBAL-005 — Все уведомления v1 являются внутренними задачами

**Given:** происходит событие, требующее уведомления  
**When:** система реагирует  
**Then:** создаётся внутренняя Task, а не Telegram/VK/SMS/email/push уведомление.

# 5. Авторизация и роли

## AC-AUTH-001 — Пользователь может войти по логину и паролю

**Given:** пользователь создан SUPER_ADMIN и имеет статус ACTIVE  
**When:** пользователь вводит корректный логин и пароль  
**Then:** система авторизует пользователя и открывает интерфейс согласно роли.

## AC-AUTH-002 — Неверные данные запрещают вход

**Given:** пользователь вводит неверный логин или пароль  
**When:** отправляет форму входа  
**Then:** система не авторизует пользователя и показывает ошибку.

## AC-AUTH-003 — Неактивный пользователь не может войти

**Given:** User.status = INACTIVE или ARCHIVED  
**When:** пользователь вводит корректные данные  
**Then:** система запрещает вход.

## AC-AUTH-004 — SUPER_ADMIN может создать пользователя

**Given:** SUPER_ADMIN авторизован  
**When:** он создаёт пользователя с ролью ADMIN или COACH  
**Then:** система создаёт User и соответствующий профиль.

## AC-AUTH-005 — COACH не может создавать пользователей

**Given:** COACH авторизован  
**When:** он пытается создать пользователя  
**Then:** UI не показывает действие, а backend запрещает запрос.

# 6. Права доступа

## AC-RBAC-001 — COACH видит только свои занятия

**Given:** COACH авторизован  
**When:** он открывает список занятий  
**Then:** он видит только занятия, где он основной тренер или назначен на замену.

## AC-RBAC-002 — COACH не видит финансовые детали

**Given:** COACH открывает занятие или карточку ребёнка  
**When:** система отображает данные  
**Then:** COACH не видит сумму оплаты, цену занятия, историю оплат, расчёт абонемента, подробные балансы или финансовые комментарии.

## AC-RBAC-003 — COACH видит только статус допуска

**Given:** COACH открывает занятие  
**When:** видит список детей  
**Then:** по ребёнку отображается только один из статусов: ADMITTED, CREDIT_LESSON_USED, NOT_ADMITTED.

## AC-RBAC-004 — COACH не может менять расписание

**Given:** COACH авторизован  
**When:** пытается создать, перенести или отменить занятие  
**Then:** действие недоступно в UI и запрещено backend.

## AC-RBAC-005 — COACH не может менять оплату и балансы

**Given:** COACH авторизован  
**When:** пытается изменить PaymentStatus, Subscription или BalanceTransaction  
**Then:** действие запрещено.

## AC-RBAC-006 — COACH не может назначать перенос

**Given:** COACH авторизован  
**When:** пытается назначить MakeupCredit  
**Then:** действие запрещено.

## AC-RBAC-007 — ADMIN видит финансовые данные

**Given:** ADMIN открывает карточку ребёнка  
**When:** система отображает данные  
**Then:** ADMIN видит абонемент, статус оплаты, баланс занятий, баланс переносов и историю операций.

## AC-RBAC-008 — Audit log недоступен COACH

**Given:** COACH авторизован  
**When:** пытается открыть Audit Log  
**Then:** доступ запрещён.

# 7. Филиалы, тренеры, группы, дети

## AC-BRANCH-001 — ADMIN может создать филиал

**Given:** ADMIN авторизован  
**When:** вводит название и сохраняет филиал  
**Then:** система создаёт Branch со статусом ACTIVE.

## AC-BRANCH-002 — Филиал требует название

**Given:** ADMIN создаёт филиал  
**When:** название пустое  
**Then:** система не сохраняет филиал.

## AC-COACH-001 — SUPER_ADMIN может создать тренера

**Given:** SUPER_ADMIN авторизован  
**When:** создаёт пользователя с ролью COACH  
**Then:** система создаёт User и CoachProfile.

## AC-COACH-002 — Логин тренера уникален

**Given:** в системе уже есть user.login = coach_1  
**When:** SUPER_ADMIN создаёт нового пользователя с таким же login  
**Then:** система показывает ошибку.

## AC-GROUP-001 — ADMIN может создать группу

**Given:** есть Branch и CoachProfile  
**When:** ADMIN создаёт группу с названием, филиалом и тренером  
**Then:** система создаёт Group со статусом ACTIVE.

## AC-GROUP-002 — Группа требует филиал и тренера

**Given:** ADMIN создаёт группу  
**When:** не выбран филиал или основной тренер  
**Then:** система не сохраняет группу.

## AC-GROUP-003 — Система показывает заполненность группы

**Given:** в группе есть дети  
**When:** ADMIN открывает список или карточку группы  
**Then:** система показывает количество активных детей.

## AC-GROUP-004 — Группа больше 15 детей создаёт задачу

**Given:** в группе стало 16 активных детей  
**When:** система пересчитывает заполненность  
**Then:** создаётся HIGH задача GROUP_OVER_CAPACITY для ADMIN.

## AC-CHILD-001 — ADMIN может создать ребёнка

**Given:** есть группа  
**When:** ADMIN создаёт ребёнка и выбирает группу  
**Then:** система создаёт Child со статусом ACTIVE.

## AC-CHILD-002 — Ребёнок не может быть в двух группах

**Given:** ребёнок уже состоит в Group A  
**When:** ADMIN пытается добавить его в Group B без перевода  
**Then:** система запрещает действие.

## AC-CHILD-003 — ADMIN может перевести ребёнка в другую группу

**Given:** ребёнок состоит в Group A  
**When:** ADMIN выбирает Group B и подтверждает перевод  
**Then:** current_group_id ребёнка меняется на Group B.

## AC-CHILD-004 — Перевод ребёнка логируется

**Given:** ADMIN перевёл ребёнка  
**When:** операция завершена  
**Then:** создаётся audit log с old_value и new_value.

## AC-CHILD-005 — COACH может видеть телефон и VK родителя

**Given:** COACH открыл своё занятие  
**When:** открывает карточку ребёнка  
**Then:** видит телефон и VK родителя.

## AC-CHILD-006 — COACH может редактировать медицинские ограничения

**Given:** COACH имеет доступ к ребёнку через своё занятие  
**When:** редактирует medical_notes  
**Then:** изменения сохраняются и пишутся в audit log.

## AC-CHILD-007 — COACH не может редактировать комментарий админа

**Given:** COACH открыл карточку ребёнка  
**When:** просматривает admin_comment  
**Then:** поле доступно только для чтения.

# 8. Расписание и занятия

## AC-SCHEDULE-001 — ADMIN может создать шаблон расписания

**Given:** есть Group, Branch и Coach  
**When:** ADMIN указывает день недели, время начала и окончания  
**Then:** система создаёт ScheduleTemplate.

## AC-SCHEDULE-002 — Шаблон требует день недели и время

**Given:** ADMIN создаёт ScheduleTemplate  
**When:** weekday или start_time пустой  
**Then:** система не сохраняет шаблон.

## AC-LESSON-001 — ADMIN может сгенерировать занятия на месяц и учебный год

**Given:** у группы есть активный ScheduleTemplate  
**When:** ADMIN выбирает месяц или год начала учебного года и подтверждает генерацию  
**Then:** система создаёт Lessons со статусом SCHEDULED; для учебного года создаются только месяцы сентябрь-май.

## AC-LESSON-002 — Генерация не создаёт дубли

**Given:** занятия на этот месяц уже существуют  
**When:** ADMIN повторно запускает генерацию  
**Then:** система предупреждает о дублях и не создаёт дубликаты без подтверждения.

## AC-LESSON-003 — ADMIN может создать ручное занятие

**Given:** есть Group, Branch и Coach  
**When:** ADMIN создаёт Lesson вручную  
**Then:** система создаёт Lesson со статусом SCHEDULED.

## AC-LESSON-004 — ADMIN может перенести занятие

**Given:** Lesson существует  
**When:** ADMIN выбирает новую дату и указывает причину  
**Then:** Lesson переносится, причина сохраняется, действие пишется в audit log.

## AC-LESSON-005 — Перенос требует причину

**Given:** ADMIN переносит Lesson  
**When:** причина не указана  
**Then:** система не выполняет перенос.

## AC-LESSON-006 — ADMIN может отменить занятие

**Given:** Lesson существует  
**When:** ADMIN выбирает причину и подтверждает отмену  
**Then:** Lesson.status = CANCELLED, списаний нет, действие пишется в audit log.

## AC-LESSON-007 — Отмена требует причину

**Given:** ADMIN отменяет Lesson  
**When:** причина не указана  
**Then:** система не отменяет занятие.

## AC-LESSON-008 — ADMIN может назначить замену

**Given:** Lesson существует и есть CoachProfile  
**When:** ADMIN назначает substitute_coach  
**Then:** тренер-замена видит занятие в своём интерфейсе.

# 9. Экран тренера и посещаемость

## AC-COACH-LESSON-001 — COACH видит список детей занятия

**Given:** COACH открыл своё занятие  
**When:** экран загрузился  
**Then:** система показывает детей текущей группы.

## AC-COACH-LESSON-002 — COACH видит медицинские ограничения

**Given:** у ребёнка есть medical_notes  
**When:** COACH открывает занятие  
**Then:** medical_notes отображаются у ребёнка.

## AC-COACH-LESSON-003 — NOT_ADMITTED заметен

**Given:** Child.admission_status = NOT_ADMITTED  
**When:** COACH открывает занятие  
**Then:** статус “Не допускать” отображается визуально заметно.

## AC-ATT-001 — PRESENT списывает 1 занятие

**Given:** у ребёнка активный баланс > 0  
**When:** COACH ставит PRESENT и сохраняет табель  
**Then:** создаётся LessonBalanceTransaction PRESENT_DEDUCTION с amount = -1.

## AC-ATT-002 — ABSENT_UNEXCUSED списывает 1 занятие

**Given:** у ребёнка активный баланс > 0  
**When:** COACH ставит ABSENT_UNEXCUSED  
**Then:** создаётся UNEXCUSED_ABSENCE_DEDUCTION с amount = -1.

## AC-ATT-003 — ABSENT_SICK_PENDING не списывает занятие

**Given:** COACH ставит ABSENT_SICK_PENDING  
**When:** табель сохранён  
**Then:** баланс ребёнка не меняется.

## AC-ATT-004 — ABSENT_SICK_PENDING создаёт задачу по справке

**Given:** COACH ставит ABSENT_SICK_PENDING  
**When:** табель сохранён  
**Then:** создаётся HIGH задача CERTIFICATE_PENDING для ADMIN.

## AC-ATT-005 — Изменение посещаемости логируется

**Given:** COACH или ADMIN меняет AttendanceRecord  
**When:** изменение сохранено  
**Then:** создаётся audit log.

## AC-ATT-006 — Lesson становится ATTENDANCE_COMPLETED после заполнения

**Given:** все дети в занятии отмечены  
**When:** табель сохранён  
**Then:** Lesson.status = ATTENDANCE_COMPLETED.

## AC-ATT-007 — Неотмеченный табель не списывает занятия

**Given:** Lesson не имеет заполненной посещаемости  
**When:** наступает 22:00  
**Then:** система создаёт задачи, но не создаёт BalanceTransaction для детей автоматически.

## AC-ATT-008 — 2 пропуска подряд создают задачу админу

**Given:** у ребёнка 2 последовательных неуважительных пропуска  
**When:** второй пропуск зафиксирован  
**Then:** создаётся задача ADMIN, тренеру задача не создаётся.

# 10. Болезни, справки, отпуск

## AC-SICK-001 — ADMIN может подтвердить болезнь

**Given:** AttendanceRecord.status = ABSENT_SICK_PENDING  
**When:** ADMIN ставит ABSENT_SICK_CONFIRMED  
**Then:** занятие не списывается и создаётся MakeupCredit.

## AC-SICK-002 — Подтверждённая болезнь создаёт транзакцию переноса

**Given:** создан MakeupCredit по болезни  
**When:** операция завершена  
**Then:** создаётся LessonBalanceTransaction SICKNESS_MAKEUP_CREATED с amount = +1 и balance_type = MAKEUP_BALANCE.

## AC-SICK-003 — Через неделю после болезни создаётся follow-up

**Given:** ABSENT_SICK_PENDING установлен 7 дней назад и не финализирован  
**When:** система выполняет проверку  
**Then:** создаётся HIGH задача SICKNESS_FOLLOW_UP для ADMIN.

## AC-SICK-004 — Справка не загружается файлом

**Given:** ADMIN работает с болезнью  
**When:** подтверждает статус  
**Then:** система не требует и не предлагает загрузку файла справки.

## AC-VAC-001 — ADMIN может оформить отпуск

**Given:** родитель заранее сообщил об отпуске вне системы  
**When:** ADMIN указывает период отпуска  
**Then:** система создаёт статусы/переносы согласно занятиям периода.

## AC-VAC-002 — Отпуск нельзя оформить задним числом

**Given:** ADMIN выбирает прошедший период  
**When:** пытается сохранить отпуск  
**Then:** система запрещает действие.

## AC-VAC-003 — Подтверждённый отпуск не списывает занятие

**Given:** AttendanceRecord final_status = ABSENT_VACATION_APPROVED  
**When:** система применяет правило  
**Then:** занятие не списывается.

## AC-VAC-004 — Подтверждённый отпуск создаёт перенос

**Given:** отпуск подтверждён  
**When:** система применяет правило  
**Then:** создаётся MakeupCredit с причиной VACATION.

## AC-VAC-005 — Файл заявления на отпуск не загружается

**Given:** ADMIN оформляет отпуск  
**When:** сохраняет статус  
**Then:** система не требует загрузить файл заявления.

# 11. Карантин, мероприятия и переносы

## AC-GEVENT-001 — ADMIN может применить карантин к группе

**Given:** есть Group и Lessons в периоде  
**When:** ADMIN выбирает QUARANTINE и период  
**Then:** система применяет массовое событие к занятиям группы.

## AC-GEVENT-002 — Карантин применяется только к группе

**Given:** ADMIN создаёт карантин  
**When:** выбирает область действия  
**Then:** доступен уровень Group, а не отдельный Child или Branch.

## AC-GEVENT-003 — Карантин создаёт переносы детям

**Given:** карантин применён к группе  
**When:** система обрабатывает детей группы  
**Then:** каждому затронутому ребёнку создаётся MakeupCredit.

## AC-GEVENT-004 — Мероприятие детского сада создаёт переносы

**Given:** ADMIN применяет KINDERGARTEN_EVENT к занятию/периоду  
**When:** событие сохранено  
**Then:** детям создаются переносы, будущая оплата уменьшается.

## AC-MAKEUP-001 — MakeupCredit отображается в карточке ребёнка

**Given:** у ребёнка создан MakeupCredit  
**When:** ADMIN открывает карточку ребёнка  
**Then:** перенос отображается в блоке переносов.

## AC-MAKEUP-002 — MakeupCredit отображается в борде переносов

**Given:** у ребёнка есть доступный перенос  
**When:** ADMIN открывает борд переносов  
**Then:** перенос отображается в соответствующей колонке/таблице.

## AC-MAKEUP-003 — Создание переноса создаёт задачу назначения

**Given:** создан MakeupCredit со статусом AVAILABLE  
**When:** assigned_lesson_id пустой  
**Then:** создаётся HIGH задача MAKEUP_NEEDS_ASSIGNMENT.

## AC-MAKEUP-004 — ADMIN может назначить дату переноса

**Given:** MakeupCredit.status = AVAILABLE  
**When:** ADMIN выбирает занятие той же группы  
**Then:** MakeupCredit.status = ASSIGNED.

## AC-MAKEUP-005 — Перенос нельзя использовать в другой группе

**Given:** MakeupCredit относится к ребёнку из Group A  
**When:** ADMIN выбирает занятие Group B  
**Then:** система запрещает назначение.

## AC-MAKEUP-006 — Перенос не имеет срока действия в v1

**Given:** MakeupCredit создан  
**When:** проходит время  
**Then:** система не должна автоматически удалять или сжигать перенос по сроку.

# 12. Абонементы, балансы, долг и допуск

## AC-SUB-001 — ADMIN может создать абонемент

**Given:** Child.status = ACTIVE  
**When:** ADMIN создаёт Subscription с периодом, количеством занятий и ценой  
**Then:** система создаёт Subscription.

## AC-SUB-002 — Создание абонемента начисляет баланс

# 23. Definition of Done для v1

v1 считается готовой к первому внутреннему использованию, если:

1. Все критичные acceptance criteria из разделов Auth, RBAC, Children, Groups, Schedule, Attendance, Subscriptions, Makeups, Tasks и Audit Log выполнены.
2. COACH может провести день занятий без помощи админа в интерфейсе.
3. ADMIN может увидеть все операционные проблемы в одном месте.
4. Система не теряет переносы.
5. Система не допускает ребёнка при NOT_ADMITTED.
6. Система не показывает финансы тренеру.
7. Система не списывает занятия при незаполненном табеле.
8. Система логирует критичные изменения.
9. Система не содержит функций, явно исключённых из v1.
10. Пользователь может пройти полный сценарий: ребёнок → группа → расписание → занятие → посещаемость → списание/перенос/допуск.

# 24. Ключевой вывод

Acceptance Criteria v1 защищают продукт от двух рисков:

```text
1. Сделать слишком мало и не закрыть операционную боль.
2. Сделать слишком много и уйти в ненужные функции.
```

Главный фокус приёмки:

```text
Посещаемость
Расписание
Абонементы
Балансы
Переносы
Долг
Допуск
Внутренние задачи
Права доступа
Audit log
```
