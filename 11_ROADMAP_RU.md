## 2. Стратегическая цель roadmap

Главная цель первой версии — не построить “идеальную CRM”, а создать рабочую операционную систему для Азбуки движения.

v1 должна закрыть ядро:

```text
Расписание
Посещаемость
Абонементы
Балансы
Переносы
Долг
Допуск
Внутренние задачи
```

После этого можно думать о расширении:

```text
Родительский интерфейс
Внешние уведомления
Онлайн-оплата
SaaS для других школ
```

---

## 3. Главный принцип разработки

Разработка должна идти не по экранам, а по операционным цепочкам.

Неправильный подход:

```text
Сначала сделать красивую админку, потом когда-нибудь добавить бизнес-логику.
```

Правильный подход:

```text
Сначала сделать минимальную цепочку:
ребёнок → группа → занятие → посещаемость → списание → задача/допуск.
```

Каждый milestone должен давать работающий кусок операционной системы.

## 5. Что важно не делать раньше времени

До завершения v1 не делать:

```text
Родительский кабинет
Онлайн-оплату
Telegram/VK/SMS/email/push уведомления
Внутренний чат
Публичный SaaS onboarding
White-label
Мобильные приложения iOS/Android
Сложную аналитику
Payroll тренеров
Полноценную бухгалтерию
```

Причина:

```text
Эти функции не решают главную боль v1 — операционный учёт занятий, списаний, переносов и допуска.
```

Сделать расписание групп и генерацию занятий.

## 10.2 Scope

```text

Ручное создание занятия
Перенос занятия
Отмена занятия
Причина переноса/отмены
Замена тренера

```

## 10.3 Основные сущности

```text
schedule_templates
lessons
```

## 10.4 Основные экраны

```text
Admin — Расписание
Admin — Карточка занятия
Coach — Мои занятия
```

## 10.5 Ключевая логика

- группа обычно имеет 2 занятия в неделю;
- занятия генерируются на месяц;
- перенос группового занятия меняет дату;
- отменённое занятие не списывает абонемент;
- причина отмены/переноса обязательна;
- тренер видит свои занятия;
- тренер видит занятия по замене.

## 10.6 Acceptance Criteria

```text
ADMIN может создать шаблон расписания.
ADMIN может сгенерировать занятия на месяц.
Дубли занятий не создаются.
ADMIN может создать ручное занятие.
ADMIN может перенести занятие с причиной.
ADMIN может отменить занятие с причиной.
ADMIN может назначить замену тренера.
COACH видит свои занятия.
COACH видит занятия, где он на замене.
COACH не видит чужие занятия.
```

## 10.7 Риски

- слишком сложно реализовать календарь сразу;
- не сделать простой список занятий;
- неправильно обработать дубли при генерации.

## 10.8 Рекомендация

Сначала сделать список занятий и базовый календарь, а не сложный drag-and-drop календарь.

COACH может сохранить табель.

Изменения посещаемости логируются.
Если табель не заполнен до 18:00, создаётся задача.

# 12. Phase 5 — Subscriptions, Balances and Admission

## 12.1 Цель

Добавить абонементы, балансы занятий, списания, долг и допуск.

## 12.2 Scope

```text
Subscription
PaymentStatus
LessonBalanceTransaction

```

## 12.3 Основные сущности

```text
subscriptions
lesson_balance_transactions
children.admission_status
children.cached_lesson_balance
children.cached_makeup_balance
```

## 12.4 Ключевая логика

```text
Создание абонемента → +N занятий
PRESENT → -1 занятие
ABSENT_UNEXCUSED → -1 занятие
Баланс 0 + PRESENT → разрешить до -1
Баланс -1 + нет оплаты → NOT_ADMITTED
COACH видит только AdmissionStatus
```

## 12.5 PaymentStatus

```text
NOT_INVOICED
INVOICED
NOT_PAID
PAID
PARTIALLY_PAID
OVERDUE
```

## 12.6 AdmissionStatus

```text
ADMITTED
CREDIT_LESSON_USED
NOT_ADMITTED
```

## 12.7 Acceptance Criteria

```text
ADMIN может создать абонемент.
Абонемент начисляет баланс через транзакцию.
PRESENT списывает 1 занятие.
ABSENT_UNEXCUSED списывает 1 занятие.
Баланс хранится через транзакции.
ADMIN может изменить PaymentStatus с комментарием.
COACH не видит финансовые детали.
COACH видит ADMITTED / CREDIT_LESSON_USED / NOT_ADMITTED.
Ребёнок может взять 1 занятие в долг.
После неоплаченного долга ребёнок становится NOT_ADMITTED.
COACH не может обойти NOT_ADMITTED.
```

## 12.8 Риски

- хранить баланс только числом;
- смешать PaymentStatus и AdmissionStatus;
- показать тренеру финансовую детализацию;
- не сделать audit log для изменений оплаты.

# 15. Phase 8 — Trial Lessons

## 15.1 Цель

Реализовать пробные занятия.

## 15.2 Scope

```text
TrialParticipant
Создание пробника админом
Добавление пробника тренером
Отображение пробника в занятии
Отметка пришёл / не пришёл
Редактирование контактов
Задача админу после пробного
Конвертация пробника в ребёнка
```

## 15.3 Ключевая логика

- первое пробное занятие бесплатное;
- пробник не является обычным ребёнком;
- поля пробника необязательные;
- тренер может добавить пробника;
- админ обрабатывает пробника после занятия;
- только админ конвертирует пробника в активного ребёнка.

## 15.4 Acceptance Criteria

```text
ADMIN может создать пробника.
COACH может добавить пробника в своём занятии.
Поля пробника необязательные.
Пробник отображается отдельным блоком.
COACH может отметить пришёл/не пришёл.
COACH может обновить контакты.
После пробного создаётся задача админу.
ADMIN может конвертировать пробника в Child.
COACH не может конвертировать пробника.
```

## 15.5 Риски
