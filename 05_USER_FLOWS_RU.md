# My School — User Flows

**Проект:** My School  
**Бизнес:** Азбука движения  
**Тип документа:** User Flows / Пользовательские сценарии  
**Версия:** v1.0  
**Дата:** 2026-06-02  
**Язык:** русский  
**Назначение:** описать основные пользовательские сценарии v1 для админов, тренеров, супер-админа и системных событий.

---

## 1. Назначение документа

Этот документ описывает ключевые пользовательские и системные сценарии первой версии продукта **My School**.

Документ используется для:

- проектирования UI;
- постановки задач Codex;
- разработки backend-логики;
- проверки бизнес-правил;
- написания acceptance criteria;
- ручного и автоматического тестирования.

Главная цепочка продукта:

```text
Ребёнок → Группа → Расписание → Занятие → Посещаемость → Списание / Перенос / Долг / Допуск
```

---

## 2. Роли

```text
SUPER_ADMIN — настраивает систему, создаёт пользователей, импортирует данные.
ADMIN — управляет операционной работой школы.
COACH — работает с занятиями и посещаемостью.
```

---

### Статусы занятия

```text
SCHEDULED
ATTENDANCE_PENDING
ATTENDANCE_COMPLETED
MOVED
CANCELLED
```

### Статусы посещаемости тренера

```text
NOT_MARKED
PRESENT
ABSENT_UNEXCUSED
ABSENT_SICK_PENDING
```

```text
ABSENT_SICK_CONFIRMED
ABSENT_VACATION_APPROVED
ABSENT_QUARANTINE
ABSENT_EVENT
ABSENT_UNEXCUSED_FINAL
```

### Статусы оплаты

```text
NOT_INVOICED
INVOICED
NOT_PAID
PAID
PARTIALLY_PAID
OVERDUE
```

### Статусы допуска

```text
ADMITTED
CREDIT_LESSON_USED
NOT_ADMITTED
```

### Приоритеты задач

```text

HIGH
MEDIUM
LOW
```

# 4. Административные flows


## Flow 1 — Первичная настройка системы

**Участник:** SUPER_ADMIN  
**Цель:** подготовить систему к работе.

### Основной сценарий

1. SUPER_ADMIN входит в систему.
2. Создаёт аккаунты админов.
3. Создаёт аккаунты тренеров.
4. Создаёт или импортирует филиалы.
5. Создаёт или импортирует группы.
6. Создаёт или импортирует детей и родителей.
7. Создаёт шаблоны расписания.
8. Проверяет корректность данных.
9. Передаёт логины и пароли пользователям вне системы.

### Системные последствия

- создаются User, AdminProfile, CoachProfile;
- создаются Branch, Group, Parent, Child;
- действия пишутся в audit log.

### Альтернативы

Если Excel содержит ошибки, система показывает строки с ошибками и не импортирует некорректные данные.

---

## Flow 2 — Создание филиала

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** добавить локацию, где проходят занятия.

### Основной сценарий

1. Пользователь открывает раздел “Филиалы”.
2. Нажимает “Создать филиал”.
3. Вводит название.
4. Вводит адрес.
5. Добавляет комментарий/заметки по инвентарю, если нужно.
6. Сохраняет филиал.

### Системные последствия

- создаётся Branch со статусом ACTIVE;
- действие пишется в audit log.

---

## Flow 3 — Создание тренера

**Участник:** SUPER_ADMIN  
**Цель:** создать тренера и выдать доступ.

### Основной сценарий

1. SUPER_ADMIN открывает “Пользователи”.
2. Создаёт пользователя с ролью COACH.
3. Вводит ФИО.
4. Задаёт логин.
5. Задаёт временный пароль.
6. Сохраняет.
7. Передаёт логин/пароль тренеру вне системы.

### Системные последствия

- создаётся User;
- создаётся CoachProfile;
- действие пишется в audit log.

---

## Flow 4 — Создание группы

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** создать группу детей.

### Основной сценарий

1. ADMIN открывает “Группы”.
2. Нажимает “Создать группу”.
3. Вводит название.
4. Выбирает филиал.
5. Выбирает основного тренера.
6. Указывает лимит/ориентир вместимости, по умолчанию 15.
7. Добавляет заметки по инвентарю.
8. Сохраняет.

### Системные последствия

- создаётся Group;
- группа привязана к Branch и CoachProfile;
- действие пишется в audit log.

---

## Flow 5 — Создание ребёнка и родителя

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** добавить ребёнка и связать его с родителем и группой.

### Основной сценарий

1. ADMIN открывает “Дети”.
2. Нажимает “Создать ребёнка”.
3. Вводит ФИО ребёнка.
4. Вводит дату рождения.
5. Система рассчитывает возраст.
6. Вводит ФИО родителя.
7. Вводит телефон родителя.
8. Вводит VK-профиль родителя, если есть.
9. Выбирает группу.
10. Заполняет медицинские ограничения, если есть.
11. Добавляет комментарии.
12. Сохраняет.

### Системные последствия

- создаётся Parent, если его ещё нет;
- создаётся Child;
- Child получает статус ACTIVE;
- Child привязан к одной Group;
- действие пишется в audit log.

### Ограничения

Ребёнок не может быть в двух активных группах одновременно.

---

## Flow 6 — Перевод ребёнка в другую группу

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** перевести ребёнка из одной группы в другую.

### Основной сценарий

1. ADMIN открывает карточку ребёнка.
2. Нажимает “Перевести в другую группу”.
3. Выбирает новую группу.
4. Указывает комментарий/причину.
5. Подтверждает перевод.

### Системные последствия

- current_group_id ребёнка обновляется;
- ребёнок больше не числится в старой группе;
- действие пишется в audit log.

### Альтернатива

Если после перевода в группе больше 15 детей, система создаёт HIGH задачу админу.

---


# 5. Расписание и занятия

## Flow 7 — Создание шаблона расписания группы

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** создать регулярное расписание группы.

### Основной сценарий

1. ADMIN открывает карточку группы.
2. Открывает вкладку “Расписание”.
3. Нажимает “Добавить шаблон”.
4. Выбирает день недели.
5. Указывает время начала.
6. Указывает время окончания.
7. Проверяет филиал и тренера.
8. Сохраняет шаблон.
9. Повторяет для второго дня, если группа занимается 2 раза в неделю.

### Системные последствия

- создаётся ScheduleTemplate;
- действие пишется в audit log.

---

## Flow 8 — Генерация занятий на месяц

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** создать занятия группы на месяц.

### Основной сценарий

1. ADMIN открывает “Расписание”.
2. Выбирает группу.
3. Нажимает “Сгенерировать занятия”.
4. Выбирает месяц.
5. Система показывает preview занятий.
6. ADMIN проверяет даты.
7. ADMIN подтверждает генерацию.

### Системные последствия

- создаются Lesson со статусом SCHEDULED;
- занятия привязаны к группе, филиалу и тренеру;
- действие пишется в audit log.

### Альтернативы

Если занятия уже сгенерированы, система предупреждает о возможных дублях.

---

## Flow 9 — Ручное создание занятия

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** создать разовое занятие вручную.

### Основной сценарий

1. ADMIN открывает расписание.
2. Нажимает “Создать занятие”.
3. Выбирает группу.
4. Выбирает дату.
5. Указывает время.
6. Выбирает тренера.
7. Добавляет комментарий.
8. Сохраняет.

### Системные последствия

- создаётся Lesson;
- действие пишется в audit log.

---

## Flow 10 — Перенос группового занятия

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** перенести занятие всей группы на другую дату.

### Основной сценарий

1. ADMIN открывает занятие.
2. Нажимает “Перенести”.
3. Выбирает новую дату.
4. Выбирает новое время, если нужно.
5. Указывает причину.
6. Подтверждает.

### Системные последствия

- дата занятия изменяется;
- статус занятия становится MOVED или сохраняет SCHEDULED с историей изменения;
- причина сохраняется;
- действие пишется в audit log.

### Ограничение

Причина переноса обязательна.

---

## Flow 11 — Отмена занятия

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** отменить занятие.

### Основной сценарий

1. ADMIN открывает занятие.
2. Нажимает “Отменить”.
3. Выбирает причину.
4. Указывает комментарий.
5. Подтверждает отмену.

### Системные последствия

- Lesson.status = CANCELLED;
- занятие не списывает абонементы;
- тренер видит, что занятие отменено;
- действие пишется в audit log.

---

## Flow 12 — Назначение замены тренера

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** назначить другого тренера на занятие.

### Основной сценарий

1. ADMIN открывает занятие.
2. Нажимает “Назначить замену”.
3. Выбирает тренера-замену.
4. Добавляет комментарий.
5. Сохраняет.

### Системные последствия

- substitute_coach_id обновляется;
- тренер-замена видит занятие;
- действие пишется в audit log.

---


# 6. Массовые события

## Flow 13 — Карантин группы

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** обработать карантин группы.

### Основной сценарий

1. ADMIN открывает группу или расписание.
2. Выбирает “Массовое событие”.
3. Выбирает группу.
4. Выбирает период.
5. Выбирает причину QUARANTINE.
6. Выбирает действие “Перенести занятия”.
7. Подтверждает.

### Системные последствия

- занятия группы в периоде переносятся;
- детям создаются MakeupCredit;
- создаются LessonBalanceTransaction;
- будущая оплата уменьшается;
- действие пишется в audit log.

### Ограничение

Карантин в v1 применяется только на уровне группы.

---

## Flow 14 — Мероприятие детского сада

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** обработать занятие/период, который не может пройти из-за мероприятия сада.

### Основной сценарий

1. ADMIN выбирает группу.
2. Выбирает занятие или период.
3. Выбирает причину KINDERGARTEN_EVENT.
4. Выбирает действие “Перенести”.
5. Подтверждает.

### Системные последствия

- занятия переносятся;
- детям создаются переносы;
- будущая оплата уменьшается;
- действие пишется в audit log.

---


# 7. Тренерские flows

## Flow 15 — Тренер входит в систему

**Участник:** COACH  
**Цель:** получить доступ к своим занятиям.

### Основной сценарий

1. COACH открывает страницу входа.
2. Вводит логин.
3. Вводит пароль.
4. Система проверяет данные.
5. Система определяет роль COACH.
6. Открывается тренерский интерфейс.

### Альтернативы

Если логин/пароль неверные или пользователь неактивен, доступ запрещён.

---

## Flow 16 — Тренер видит сегодняшние занятия

**Участник:** COACH  
**Цель:** быстро увидеть свои занятия на сегодня.

### Основной сценарий

1. COACH открывает главный экран.
2. Система показывает занятия на сегодня.
3. Для каждого занятия отображается:
   - время;
   - группа;
   - филиал;
   - адрес;
   - статус занятия;
   - статус табеля;
   - наличие пробников;
   - важные предупреждения.
4. COACH выбирает занятие.

### Ограничение

COACH видит только свои занятия и занятия, где он назначен на замену.

---

## Flow 17 — Тренер отмечает посещаемость

**Участник:** COACH  
**Цель:** заполнить табель занятия.

### Основной сценарий

1. COACH открывает занятие.
2. Система показывает список детей.
3. По каждому ребёнку отображается:
   - ФИО;
   - возраст;
   - медицинские ограничения;
   - комментарий админа;
   - статус допуска;
   - предварительная отметка болезни, если есть.
4. COACH выбирает статус:
   - PRESENT;
   - ABSENT_UNEXCUSED;
   - ABSENT_SICK_PENDING.
5. COACH сохраняет табель.
6. Система применяет бизнес-правила.
7. Система обновляет статус занятия.
8. Система пишет audit log.

### Системные последствия

```text
PRESENT → списать 1 занятие.
ABSENT_UNEXCUSED → списать 1 занятие.
ABSENT_SICK_PENDING → не списывать, ждать админа.
```

### Ограничение

Если ребёнок `NOT_ADMITTED`, COACH не может обойти блокировку.

---

## Flow 18 — Тренер редактирует посещаемость

**Участник:** COACH  
**Цель:** исправить ошибку в табеле.

### Основной сценарий

1. COACH открывает прошедшее занятие.
2. Изменяет статус посещаемости.
3. Сохраняет.
4. Система пересчитывает последствия, если нужно.
5. Система пишет audit log.

### Правило

Тренер может редактировать посещаемость без ограничения по времени, но все изменения должны логироваться.

---

## Flow 19 — Тренер редактирует медицинские ограничения

**Участник:** COACH  
**Цель:** обновить важную информацию по ребёнку.

### Основной сценарий

1. COACH открывает карточку ребёнка из занятия.
2. Редактирует медицинские ограничения.
3. Сохраняет.
4. Система пишет audit log.

---

## Flow 20 — Тренер оставляет комментарий по ребёнку

**Участник:** COACH  
**Цель:** оставить наблюдение тренера.

### Основной сценарий

1. COACH открывает карточку ребёнка.
2. Редактирует тренерский комментарий.
3. Сохраняет.

### Ограничение

COACH не может редактировать комментарий админа.

---


# 8. Системные flows по посещаемости

## Flow 21 — Табель не заполнен до 18:00

**Участник:** SYSTEM  
**Цель:** создать задачи, если тренер не заполнил посещаемость.

### Основной сценарий

1. В 18:00 система проверяет занятия за день.
2. Находит занятия без заполненной посещаемости.
3. Создаёт задачу тренеру.
4. Создаёт задачу админу.
5. Приоритет задач — CRITICAL.

### Важное правило

Система не списывает занятия автоматически, если табель не заполнен.

---

## Flow 22 — Ребёнок присутствовал

**Участник:** COACH / SYSTEM  
**Цель:** списать занятие за присутствие.

### Основной сценарий

1. COACH ставит PRESENT.
2. Система проверяет допуск.
3. Если ребёнок ADMITTED, система списывает 1 занятие.
4. Создаётся LessonBalanceTransaction типа PRESENT_DEDUCTION.
5. Действие пишется в audit log.

### Альтернатива

Если баланс = 0, система может разрешить 1 занятие в долг.

---

## Flow 23 — Ребёнок отсутствовал без причины

**Участник:** COACH / SYSTEM  
**Цель:** списать занятие за неуважительное отсутствие.

### Основной сценарий

1. COACH ставит ABSENT_UNEXCUSED.
2. Система списывает 1 занятие.
3. Создаётся LessonBalanceTransaction типа UNEXCUSED_ABSENCE_DEDUCTION.
4. Если у ребёнка 2 пропуска подряд, создаётся задача админу.
5. Действие пишется в audit log.

---

## Flow 24 — Родитель сообщил тренеру о болезни

**Участник:** COACH / SYSTEM / ADMIN  
**Цель:** зафиксировать болезнь без списания.

### Основной сценарий

1. Родитель сообщает тренеру в VK/мессенджере.
2. COACH ставит ABSENT_SICK_PENDING.
3. Система не списывает занятие.
4. Ситуация попадает в контроль админа.
5. Через неделю создаётся задача админу проверить статус болезни.

---

## Flow 25 — Админ подтверждает болезнь

**Участник:** ADMIN / SYSTEM  
**Цель:** подтвердить болезнь и создать перенос.

### Основной сценарий

1. ADMIN открывает отсутствие со статусом ABSENT_SICK_PENDING.
2. Проверяет справку/подтверждение вне системы.
3. Ставит ABSENT_SICK_CONFIRMED.
4. Система не списывает занятие.
5. Система создаёт MakeupCredit.
6. Система создаёт LessonBalanceTransaction.
7. Будущая оплата уменьшается.
8. Действие пишется в audit log.

---

## Flow 26 — Админ финализирует отсутствие без причины

**Участник:** ADMIN  
**Цель:** закрыть отсутствие, причина которого была неясна.

### Основной сценарий

1. ADMIN открывает блок “Отсутствия без финальной причины”.
2. Проверяет информацию во внешних чатах.
3. Выбирает финальный статус:
   - ABSENT_SICK_CONFIRMED;
   - ABSENT_VACATION_APPROVED;
   - ABSENT_UNEXCUSED_FINAL;
   - ABSENT_EVENT;
   - ABSENT_QUARANTINE.
4. Система применяет соответствующие бизнес-правила.
5. Действие пишется в audit log.

---


# 9. Отпуск, переносы и балансы

## Flow 27 — Админ оформляет отпуск

**Участник:** ADMIN  
**Цель:** зафиксировать заранее согласованный отпуск.

### Основной сценарий

1. ADMIN открывает карточку ребёнка.
2. Выбирает “Оформить отпуск”.
3. Указывает период.
4. Добавляет комментарий.
5. Подтверждает.
6. Система находит занятия ребёнка в периоде.
7. Система ставит ABSENT_VACATION_APPROVED.
8. Занятия не списываются.
9. Система создаёт переносы.
10. Будущая оплата уменьшается.
11. Действие пишется в audit log.

### Ограничение

Отпуск нельзя оформить задним числом.

---

## Flow 28 — Админ назначает дату переноса

**Участник:** ADMIN  
**Цель:** назначить дату использования переноса.

### Основной сценарий

1. ADMIN открывает борд переносов.
2. Находит перенос ребёнка.
3. Нажимает “Назначить дату”.
4. Выбирает занятие в той же группе.
5. Подтверждает.
6. Статус MakeupCredit становится ASSIGNED.
7. Действие пишется в audit log.

### Ограничение

Перенос нельзя использовать в другой группе.

---

## Flow 29 — Использование переноса

**Участник:** ADMIN / SYSTEM  
**Цель:** отметить перенос как использованный.

### Основной сценарий

1. ADMIN открывает перенос.
2. Отмечает “Использован”.
3. Система меняет статус MakeupCredit на USED.
4. Создаёт BalanceTransaction типа MAKEUP_USED.
5. Действие пишется в audit log.

---

## Flow 30 — Ручная корректировка баланса

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** исправить баланс в исключительной ситуации.

### Основной сценарий

1. ADMIN открывает карточку ребёнка.
2. Открывает историю баланса.
3. Нажимает “Ручная корректировка”.
4. Выбирает тип баланса.
5. Указывает значение +N или -N.
6. Вводит обязательный комментарий.
7. Подтверждает.
8. Система создаёт MANUAL_ADJUSTMENT.
9. Действие пишется в audit log.

### Ограничение

Комментарий обязателен.

---


# 10. Абонементы, оплата и допуск

## Flow 31 — Создание абонемента

**Участник:** ADMIN / SUPER_ADMIN  
**Цель:** создать ребёнку абонемент с лимитом занятий.

### Основной сценарий

1. ADMIN открывает карточку ребёнка.
2. Нажимает “Создать абонемент”.
3. Указывает период.
4. Указывает количество занятий.
5. Указывает цену занятия, по умолчанию 450 рублей.
6. Указывает статус оплаты.
7. Добавляет комментарий.
8. Сохраняет.
9. Система создаёт Subscription.
10. Система создаёт LessonBalanceTransaction типа SUBSCRIPTION_CREATED.
11. Баланс занятий увеличивается на N.
12. Действие пишется в audit log.

---

## Flow 32 — Расчёт оплаты при старте в середине месяца

**Участник:** ADMIN  
**Цель:** рассчитать оплату за оставшиеся занятия месяца.

### Основной сценарий

1. ADMIN выбирает дату старта ребёнка.
2. Система определяет оставшиеся занятия группы до конца месяца.
3. Система умножает количество оставшихся занятий на цену занятия.
4. ADMIN проверяет расчёт.
5. ADMIN создаёт абонемент.

### Формула

```text
Сумма = количество оставшихся занятий × цена занятия
```

---

## Flow 33 — Расчёт следующего месяца с переносами

**Участник:** ADMIN / SYSTEM  
**Цель:** уменьшить будущую оплату с учётом переносов.

### Основной сценарий

1. Система определяет количество занятий следующего месяца.
2. Система определяет количество доступных переносов/остатков.
3. Система рассчитывает оплачиваемое количество занятий.
4. ADMIN проверяет расчёт.
5. ADMIN создаёт или обновляет абонемент.

### Формула

```text
К оплате занятий = занятия следующего месяца - переносы/остатки
Сумма = к оплате занятий × цена занятия
```

---

## Flow 34 — Изменение статуса оплаты

**Участник:** ADMIN  
**Цель:** отразить ручную оплату/квитанцию.

### Основной сценарий

1. ADMIN открывает карточку ребёнка или абонемент.
2. Меняет статус оплаты.
3. Вводит обязательный комментарий.
4. Сохраняет.
5. Система сохраняет дату изменения.
6. Система пишет audit log.
7. При необходимости обновляется AdmissionStatus.

### Ограничение

Комментарий обязателен.

---

## Flow 35 — Ребёнок берёт занятие в долг

**Участник:** COACH / SYSTEM / ADMIN  
**Цель:** разрешить одно занятие в долг.

### Основной сценарий

1. COACH отмечает ребёнка PRESENT.
2. Система видит, что баланс = 0.
3. Система разрешает списание до -1.
4. AdmissionStatus становится CREDIT_LESSON_USED.
5. Создаётся CRITICAL задача админу.
6. Тренер видит, что ребёнок взял занятие в долг.
7. Действие пишется в audit log.

---

## Flow 36 — Ребёнок не допущен к следующему занятию

**Участник:** SYSTEM / COACH / ADMIN  
**Цель:** заблокировать занятие после неоплаченного долга.

### Основной сценарий

1. Баланс ребёнка = -1.
2. Оплата не внесена.
3. Наступает следующее занятие.
4. Система устанавливает AdmissionStatus = NOT_ADMITTED.
5. COACH видит “Не допускать”.
6. COACH не может обойти блокировку.
7. ADMIN видит задачу в операционном центре.

# 11. Пробные занятия

## Flow 37 — Админ создаёт пробника

**Участник:** ADMIN  
**Цель:** записать ребёнка на бесплатное пробное занятие.

### Основной сценарий

1. ADMIN открывает “Пробные занятия”.
2. Нажимает “Создать пробника”.
3. Заполняет известные поля:
   - имя ребёнка;
   - возраст;
   - имя родителя;
   - телефон;
   - VK;
   - источник;
   - дата;
   - группа;
   - тренер;
   - комментарий.
4. Сохраняет.
5. Система создаёт TrialParticipant.
6. Пробник отображается у тренера внутри занятия.

### Правило

Поля пробника в v1 необязательные.

---

## Flow 38 — Тренер добавляет пробника

**Участник:** COACH  
**Цель:** добавить пробника, если он появился на занятии или данные собрал тренер.

### Основной сценарий

1. COACH открывает занятие.
2. В блоке “Пробники” нажимает “Добавить”.
3. Вводит доступные данные.
4. Сохраняет.
5. Система создаёт TrialParticipant.
6. Действие пишется в audit log.

---

## Flow 39 — Тренер отмечает пробника

**Участник:** COACH  
**Цель:** отметить, пришёл пробник или нет.

### Основной сценарий

1. COACH открывает занятие.
2. Видит блок “Пробники”.
3. Для пробника выбирает:
   - пришёл;
   - не пришёл;
   - контакты собраны.
4. Обновляет контактные данные, если нужно.
5. Сохраняет.
6. После занятия создаётся HIGH задача админу обработать пробника.

---

## Flow 40 — Админ обрабатывает пробника

**Участник:** ADMIN  
**Цель:** принять решение после пробного занятия.

### Основной сценарий

1. ADMIN открывает задачу по пробнику.
2. Открывает карточку TrialParticipant.
3. Проверяет контакты и комментарии тренера.
4. Принимает решение:
   - конвертировать в активного ребёнка;
   - оставить в работе;
   - закрыть как неактуального.
5. Если конвертирует:
   - создаётся Child;
   - создаётся/связывается Parent;
   - назначается группа;
   - Child.status = ACTIVE.
6. Задача закрывается.
7. Действие пишется в audit log.

## Flow 43 — Админ создаёт задачу вручную

# 14. Excel-импорт

## Flow 46 — Импорт стартовых данных из Excel

**Участник:** SUPER_ADMIN  
**Цель:** загрузить стартовые данные.

### Основной сценарий

1. SUPER_ADMIN открывает раздел импорта.
2. Загружает Excel-файл.
3. Система создаёт ImportBatch.
4. Система валидирует листы и строки.
5. Система показывает preview.
6. SUPER_ADMIN подтверждает импорт.
7. Система создаёт сущности.
8. Система показывает результат импорта.

Если есть ошибки, система показывает строки с ошибками и не импортирует некорректные данные.

# 19. Общие acceptance criteria по User Flows

v1 соответствует пользовательским сценариям, если:

1. SUPER_ADMIN может создать пользователей.
2. ADMIN может создать филиал, тренера, группу, ребёнка и расписание.
3. Система не позволяет ребёнку быть в двух группах одновременно.
4. ADMIN может сгенерировать занятия на месяц.
5. ADMIN может перенести, отменить и вручную создать занятие.
6. ADMIN может назначить замену тренера.
7. COACH видит только свои занятия и замены.
8. COACH может открыть занятие и отметить посещаемость.
9. PRESENT списывает 1 занятие.
10. ABSENT_UNEXCUSED списывает 1 занятие.
11. ABSENT_SICK_PENDING не списывает занятие.
12. ADMIN может подтвердить болезнь и создать перенос.
13. ADMIN может оформить отпуск без хранения файла.
14. ADMIN может применить карантин на уровне группы.
15. Переносы отображаются в карточке ребёнка и борде.
16. Долг до -1 разрешён один раз.
17. После долга без оплаты ребёнок становится NOT_ADMITTED.
18. COACH не может обойти NOT_ADMITTED.
19. COACH не видит финансовые детали.
20. В 18:00 создаются задачи по незаполненному табелю.
21. Через неделю после болезни создаётся задача админу.
22. Пробник отображается отдельным блоком в занятии.
23. После пробного занятия создаётся задача админу.
24. Все критичные изменения пишутся в audit log.
25. Excel-импорт валидирует данные и показывает ошибки.
26. Задачи остаются открытыми до закрытия.
27. Запрещённые действия COACH недоступны в UI и заблокированы backend.

# 20. Границы v1

В User Flows v1 намеренно отсутствуют сценарии:

- родитель входит в систему;
- родитель оплачивает онлайн;
- родитель загружает справку;
- родитель пишет в чат внутри системы;
- тренер получает Telegram/VK/push-уведомление;
- система отправляет SMS/email;
- бухгалтер работает в отдельном интерфейсе;
- школа подключается как SaaS-клиент;
- родитель выбирает дату переноса самостоятельно.

Эти сценарии относятся к будущим версиям и не должны реализовываться в v1.
